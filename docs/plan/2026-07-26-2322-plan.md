# DI 测试与 NI USB-6259 实时刺激实施计划

## 一、目标与默认解释

本方案实现 `mbddf.di_read`，保留现有运行方式：

- “单次”继续对应 BIZ `single`：发送一次 `DI_READ`，产生一个样本和结果。
- “连续”继续对应 BIZ `pc_periodic`：由 BIZ 按间隔重复执行；浏览器不得用定时器重复发送 `start`。
- 不启用 `device_stream`。
- 浏览器增加 16 路实时开关。开关改变 NI-6259 输出电平，下一次 DUT `DI_READ` 样本显示板上 DI 回读。
- 初期只给 React/Web 界面增加开关面板；TUI、Qt GUI 仍能选择并运行 DI 单次/连续测试，但不新增开关控件。

这里必须明确：NI-6259 要作为 DUT DI 的外部刺激源，因此使用的是 NI-6259 **DO**：

```text
浏览器 switch
  -> WebSocket
  -> TestApplicationController
  -> 算法层 DiStimulusController
  -> HAL IDigitalIo::writeDoBatch
  -> Vendor C ABI
  -> NI-DAQmx
  -> NI-6259 DO
  -> DUT DI 引脚

浏览器单次/连续测试
  -> BIZ
  -> mbddf.di_read
  -> HalControlTransport
  -> DUT DI_READ
  -> di_state[0]/di_state[1]
```

如果“作为板上 DI 的输入”实际是指让 NI-6259 自己采集信号，而不是驱动 DUT DI，新会话应停在实施前确认；只配置为 DI 的通道无法被界面 switch 改变电平。

## 二、已核对的当前状态

- DUT 已实现 `DI_READ 0x04/0x01`，CSV 响应包含 `di_state[0]`、`di_state[1]` 两个 `U32`。
- DUT `DidoDevice` 实际读取 16 路输入；当前 `di_state[0]` 承载位图，`di_state[1]` 固定为 `0`。因此首版界面只做 16 个开关，不把 NI-6259 的 48 路全部误当成 DUT DI。
- 宿主 `IDigitalIo`、`writeDoBatch()` 和 Adapter ABI v1 的批量数字写函数已存在，不需要修改公共 HAL API 或升级 ABI。
- `CAbiAdapter` 目前完全委托 `MockAdapter`，`AdapterLoader` 尚未进入生产调用链；`HalService` 也只有一个后端。仅增加 JSON 无法连接 NI-DAQmx。
- 控制器目前只打开 DUT 一个会话，缺少第二块测试设备的生命周期。
- `frontend_launch_options.cpp` 识别六个算法，但 `TestApplicationController::loadConfigurations()` 的源码白名单仍只接受两个，和准备阶段的六个分支、现行文档不一致。新增 DI 前必须先合并为单一算法注册表。

因此本需求不能只改配置文件，必须补通 Vendor Adapter、多设备 HAL、应用动作和前端协议。

## 三、目标配置结构

在 `configs/mbddf_pc_hal.json` 中增加可选 Vendor Adapter、NI 设备和逐线资源。实际交付 JSON 应显式列出 16 路，下面只展示结构：

```jsonc
{
  "adapters": {
    "ni.daqmx": {
      "providerId": "vendor.cabi",
      "libraryPath": "${HWTEST_NI_DAQMX_ADAPTER_PATH}",
      "settings": {
        "deviceName": "Dev1",
        "expectedProductType": "USB-6259",
        "serialNumber": "CONFIGURE_ME"
      }
    }
  },
  "hardware": {
    "devices": [
      { "alias": "mbddf_dut", "adapterId": "mock.adapter.v1" },
      {
        "alias": "ni6259_stimulus",
        "adapterId": "ni.daqmx",
        "vendor": "NI",
        "model": "USB-6259"
      }
    ],
    "resources": {
      "DUT_DI0_STIM": {
        "device": "ni6259_stimulus",
        "adapterId": "ni.daqmx",
        "providerId": "vendor.cabi",
        "module": "digital",
        "direction": "output",
        "physicalIndex": 0,
        "properties": { "portNumber": 0, "lineNumber": 0 }
      }
    }
  },
  "safeState": {
    "DUT_DI0_STIM": "Low",
    "DUT_DI8_STIM": "High"
  }
}
```

`deviceName`、型号、序列号、`adapterId`、DLL 路径、端口号和线号都来自部署配置。以 6259 为例使用 `Dev1/port0/line0:15`；代码不得硬编码 `Dev1` 或端口 0。

新增 `configs/mbddf_di.testcfg.json`：

- `algorithmId = "mbddf.di_read"`。
- 协议配置使用现有 `di_read_request`、`di_read_response`。
- `hardwareRequirements` 声明 `ni.daqmx`、数字输出模块及 16 个逻辑资源。
- `executionConfig.digitalStimulus.channels` 配置 `switchId`、DUT bit、逻辑资源、展示名和 `activeLevel`。
- `reportFields.supportedRunModes = ["single", "pc_periodic"]`。
- 判定继续只依据 `status == 0`、`err_code == 0`，保持原 DI 读取/显示语义。刺激值与 DUT 位图不一致在界面警示，不在用户切换中的过渡周期制造测试失败。
- `settlingMs` 配置不一致提示的屏蔽窗口，例如 `20 ms`。

## 四、实施步骤

1. **新会话实施前门禁**

   读取仓库及 `src/hal/AGENTS.md`，检查 `git status`，保留已有修改。确认 NI-DAQmx 64 位开发支持已安装、`NIDAQmx.h`/`NIDAQmx.lib` 可用、MAX 中设备名和序列号、DUT DI 接线表、每路有效极性及安全电平。未确认共地、电压兼容或隔离/电平转换前，只实现 Mock 与编译链，不对真实端口写电平。

2. **统一 MB_DDF 算法注册**

   在 `src/app/` 增加私有算法注册表，集中保存算法 ID、请求/响应 profile、命令名和执行器工厂。`frontend_launch_options.cpp`、配置加载校验和 `prepare()` 共用该表，先修复当前“发现六项、控制器只接受两项”的分裂，再注册 `mbddf.di_read`。增加回归测试，保证目录中每个受支持配置都能被发现并加载。

3. **补通 HAL 多 Adapter 路由**

   在 `src/hal/src/` 增加私有 `AdapterRouter`，按设备 `adapterId` 懒加载 `MockAdapter` 或 `CAbiAdapter`。重构 `HalService`，使每个会话记录自己的后端，生成全局不冲突的 SessionId，并在最后一个会话关闭后卸载对应 DLL。

   `ResourceMapper` 应继承设备的 `adapterId`，多设备配置下拒绝未知设备、资源/设备 Adapter 不一致和重复物理通道，不再静默回退到第一个设备。现有单设备旧配置保持兼容。

4. **让 CAbiAdapter 真正调用 ABI v1**

   修改 `c_abi_adapter.*`，使用现有 `AdapterLoader` 完成 DLL 加载、host callback、初始化、设备句柄管理、能力查询及数字批量读写。空函数指针返回 `NotSupported`；厂家状态映射到现有 `HalStatusCode`，保留 vendor code 和扩展错误文本。

   不修改 `hal_adapter_abi.h`：现有 `digitalRead`、`digitalWrite`、`structSize` 已满足需求。`HalDevice::applySafeState()` 要把同一数字 bank 的安全值合并为一次 `writeDigitalBatch()`，避免逐线切换产生中间危险组合。

5. **实现 NI-DAQmx Vendor Adapter DLL**

   新增 `src/adapters/ni_daqmx/` 可选共享库目标 `hwtest_adapter_ni_daqmx`。通过 `HWTEST_ENABLE_NI_DAQMX`、`NI_DAQMX_INCLUDE_DIR`、`NI_DAQMX_LIBRARY` 控制构建；默认无 NI SDK 的构建仍必须成功。

   Adapter 初始化时枚举设备并校验 `deviceName/productType/serialNumber`。每个端口 bank 使用持久 DAQmx Task；6259 示例把 `port0/line0:15` 建成一个 `ChanForAllLines` DO 通道，用 `DAQmxWriteDigitalU32` 整幅写 16 位 mask。Task 在打开时启动一次，切换时不反复启动/停止；关闭时先写安全 mask，再 `StopTask/ClearTask`。禁止自动调用会影响整块卡其他任务的 `DAQmxResetDevice`。

   同步实现 `digitalRead` 的 `CreateDIChan/ReadDigitalU32`，供 Adapter 自检和后续复用，但 DUT DI 的事实仍来自产品协议 `DI_READ`。

6. **增加 DI 算法与刺激控制器**

   `MbdDfExchangeAlgorithmExecutor` 复用现有 CSV 请求/响应交换，实现 `mbddf.di_read`。在算法层新增 `DiStimulusController`：解析 `executionConfig.digitalStimulus`，只接受配置白名单中的 `switchId`，把逻辑 active/inactive 映射为物理 High/Low，并始终调用 HAL `writeDoBatch()` 写完整 mask。

   刺激控制器保存 `appliedMask`、`revision`、最后写入时间和错误；不持有 NI 类型或直接调用厂家 SDK。BIZ 不作修改，也不接触 HAL。

7. **扩展共享应用控制器和 WebSocket**

   `TestApplicationController` 保存所有已打开的设备会话；DI 配置准备时先打开 NI 设备并施加安全态，再打开 DUT 会话，任一步失败都按反序收尾。非 DI 测试不加载 NI DLL，原六项在未安装 NI 驱动时仍可运行。

   追加 `DigitalSwitchDescriptor`、`DigitalStimulusSnapshot` DTO，以及 `setDigitalStimulus(switchId, active, expectedRevision)`、`resetDigitalStimulus()` 动作。写动作只允许在 `ready/running/paused/finished/stopped`，其余阶段返回明确状态错误。停止、断开和退出固定执行“停止 BIZ -> NI 安全态 -> 关闭 NI -> 关闭 DUT -> 卸载 Adapter”。

   WebSocket v1 做追加式扩展：新增同名动作和完整刺激快照，严格校验参数；客户端不得提交 Adapter、端口、ResourceId 或本地路径。旧客户端可忽略新增字段，无需升级协议主版本。

8. **实现 React 实时开关面板**

   在 `front/src/features/` 增加 DI 专用面板，由 descriptor 生成 16 个开关。每路同时显示配置名称、刺激状态和最新 DUT 回读位；`di_state[0]` 更新时刷新回读，`di_state[1]` 保留诊断显示但不生成额外开关。

   快速连续点击使用短时合并和单请求队列，携带 revision；成功后采用后端 applied 状态，失败或 revision 冲突时回滚并显示错误。提供一个带复位图标的“恢复安全态”命令。切换动作不自动发起测试；连续模式等待下一轮 BIZ 样本，单次模式由用户设置开关后点击开始。

9. **同步事实源**

   更新 HAL、WebSocket、设备通讯、五层架构和测试规范；只有代码落地后才把 Vendor Adapter、多后端和第七个测试项写成“当前实现”。未完成真实台架验收时明确记录“NI-DAQmx 路径已实现，USB-6259 真实硬件未验收”。DUT 协议和 DUT 源码无需修改。

## 五、官方 C/C++ 参考与代码骨架

NI 官方规格确认 USB-6259 有 48 路逐端子可配置方向的 DIO：`P0.0..31`、`P1.0..7`、`P2.0..7`；本方案只占用 P0 的前 16 路。[USB-6259 规格](https://www.ni.com/docs/en-US/bundle/pci-pcie-pxi-pxie-usb-6259-specs/page/specs.html)、[DAQmx 物理通道语法](https://www.ni.com/docs/en-US/bundle/ni-daqmx/page/physchannames.html)。

NI 官方说明 ANSI C 工程包含 `NIDAQmx.h`、链接 `NIDAQmx.lib`，安装示例位于 `NI-DAQ\Examples\DAQmx ANSI C`。[ANSI C 工程说明](https://www.ni.com/docs/en-US/bundle/ni-daqmx/page/ansi-c-application-without-labwindowscvi.html)、[示例位置](https://www.ni.com/docs/en-US/bundle/ni-daqmx/page/finding-examples.html)。

Adapter 中采用的 C++ RAII 代码骨架为：

```cpp
TaskHandle task{};
DAQmxCreateTask("", &task);
DAQmxCreateDOChan(task, "Dev1/port0/line0:15", "",
                  DAQmx_Val_ChanForAllLines);
DAQmxStartTask(task);
DAQmxWriteDigitalU32(task, 1, false, timeoutSeconds,
                     DAQmx_Val_GroupByChannel, &mask, &written, nullptr);
// 析构/关闭：写安全 mask -> DAQmxStopTask -> DAQmxClearTask
```

对应官方 API：[DAQmxCreateDOChan](https://www.ni.com/docs/en-US/bundle/ni-daqmx-c-api-ref/page/group__ni-daqmx__c__functions__channel__configuration__creation__create__digital__output__channels_1ga4c427c02d6bd600f95455e07da8e41e4.html)、[DAQmxWriteDigitalU32](https://www.ni.com/docs/en-US/bundle/ni-daqmx-c-api-ref/page/group__ni-daqmx__c__functions__write__functions_1ga9f0409acaa7547cd0e8060524dcbcd6d.html)、[DAQmxStartTask](https://www.ni.com/docs/en-US/bundle/ni-daqmx-c-api-ref/page/group__ni-daqmx__c__functions__task__configuration__control_1gad8cfe18834963aa261b1f8ca9277daaa.html)、[DAQmxClearTask](https://www.ni.com/docs/en-US/bundle/ni-daqmx-c-api-ref/page/group__ni-daqmx__c__functions__task__configuration__control_1gaa5ef42ec35d41eb8f815a95247b22dc7.html)。

## 六、验证步骤

自动化验证先使用 Fake NI API 和测试 Adapter DLL，不依赖真实驱动：

```powershell
$env:MB_DDF_PROTOCOL_CSV_DIR = "H:\Resources\RTLinux\Demos\MB_DDF_v2\docs\design\product_protocol_csv"
cmake -S . -B build_vs -G "Visual Studio 17 2022" -A x64 -DBUILD_TESTING=ON
cmake --build build_vs --config Debug --parallel
ctest --test-dir build_vs -C Debug --output-on-failure
cmake --build build_vs --config Release --parallel
ctest --test-dir build_vs -C Release --output-on-failure
```

新增覆盖包括：多 Adapter 路由、DLL 生命周期、状态映射、端口/线配置校验、批量安全态、驱动缺失、超时、设备断开；DI 协议 golden、序号/CRC、单次一轮、PC 周期多轮；控制器双设备准备和反序收尾；WebSocket 动作白名单、revision 冲突和断开安全态；前端快速点击合并、失败回滚、active-low 显示和回读位解析。

NI SDK 构建另开目录并显式启用 Adapter。真实硬件用例使用 `hardware;ni_daqmx` 标签或单独开关，绝不进入默认 CTest。

前端修改后必须执行：

```powershell
Set-Location front
npm test
npm run build
```

并检查 `front/dist/index.html` 可直接双击、没有残留 `dist/assets/` 或外链 JS/CSS。本轮及下一会话都不因验证自动启动常驻后端或 Vite。

## 七、真实台架验收

在隔离接线和安全电平确认后：

1. 记录 NI-DAQmx 版本、6259 型号/序列号、MAX 设备名、端口、DUT 提交及 16 路接线表。
2. `prepare` 后确认所有通道先进入配置安全态。
3. 逐路切换 DI0..DI15，每次执行单次测试，确认只改变对应 `di_state[0]` bit。
4. 特别验证已知高有效 DI0..DI3 和低有效 DI8；其他通道按批准接线表解释。
5. 启动 `pc_periodic`，运行中连续切换，确认开关写入、样本序号、周期数和界面回读稳定。
6. 验证停止、断开、正常退出、DAQmx 错误和 USB 拔出路径；软件只能保证正常/可执行异常路径的 best-effort 安全态，进程崩溃或主机掉电必须依赖外部上拉/下拉、隔离或安全继电器。

## 八、完成标准与新会话交接

完成时必须满足：原六项行为及单次/周期语义无回归；DI 可通过配置选择；6259 Adapter、设备名、端口号、线号、极性和安全态均不硬编码；浏览器只能操作配置白名单 switch；16 路开关可实时写入并在后续 DUT 样本中看到回读；断开必走安全收尾；无 NI SDK 的默认构建仍通过；单文件前端已重新打包；真实硬件证据与 Mock/Adapter 测试证据明确区分。

新会话从“实施前门禁”开始，按上述 1 至 9 顺序执行。若确认 NI 卡应当采集而非输出、接线电平不兼容、缺少安全态定义或 16 路映射不明确，应在第一次真实写入前停止并报告，不自行猜测。当前 Plan Mode 未修改任何文件。
