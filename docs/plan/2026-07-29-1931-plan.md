# 目标

1. 将 `pc_periodic.intervalMs` 合法范围从 `10..3600000` 放宽为 `0..3600000`。
2. 明确 `intervalMs=0` 表示上一轮完整收发结束后不增加额外等待，立即开始下一轮；所有 `executeStep()` 仍严格串行，绝不并行或重入。
3. 将后端到浏览器的高频遥测改为协商式批量传输，降低 WebSocket 帧数、JSON 解析、诊断对象创建和 React 重绘压力。
4. 健康 WebSocket 连接中不丢弃、不降采样、不改序任何 `ApplicationSample`；完整持久化数据仍以启用保存后的后端 TXT 为事实源。
5. 浏览器继续只保留 50,000 点有界展示缓存，明确显示累计接收、缓存淘汰和序号完整性，不使用无限内存保存整场历史。
6. 保持设备协议、算法、HAL、DUT、`device_stream`、硬件 STOP、数据保存和后处理分析语义不变。

预计正常显示延迟上界约为：

```text
20 ms 后端批窗口 + 100 ms 前端 UI 提交窗口 ≈ 120 ms
```

开始、暂停、停止、错误和终态不进入普通遥测延迟窗口，仍立即投影。

# 设计选择

采用“WebSocket v1 显式协商批量投影”：

- 新后端默认继续发送旧 `type:"sample"`，旧前端行为完全不变。
- `hello` 追加批传 capability；新前端检测到能力后，在测试开始前发送 `setTelemetryDelivery`，协商 `batch` 模式。
- 新前端连接旧后端时因没有 capability，自动保持单条模式。
- 不升级到 v2，不增加 ACK、历史缓存或重放协议。
- 不采用“延迟后仍逐帧发送”的方案，因为它不能减少浏览器 `onmessage` 和 JSON 解析次数。
- 不采用无限出站队列；慢客户端达到硬水位时明确报错并安全收尾，禁止静默丢样本。

“完整数据”的边界定义为：

- 健康连接期间，WebSocket 批次包含后端投影的每一条有效样本。
- 浏览器通过序号检查证明是否存在缺口。
- 浏览器环形缓存覆盖旧点不等于网络丢样本，必须单独显示淘汰计数。
- 重连前历史不缓存、不重放；长时全量记录由后端 TXT 保证。
- 若浏览器长期慢于数据源，不可能同时保证全样本、永不断线和有界内存；达到背压硬上限时必须显式失败。

# 实施步骤

## 1. 先补零间隔回归测试

在 `test_run_service_test.cpp` 中先建立失败用例：

1. `intervalMs=0, maxCycles=3` 执行恰好三轮。
2. 记录 `executeStep()` 活动计数，断言最大并发数始终为 `1`。
3. 断言轮次严格为 `1,2,3`，结果和样本的 `cycleIndex` 正确。
4. 断言 `prepare()` 和 `finishRun()` 各执行一次。
5. 断言 `TestContext.tags.intervalMs == 0`。
6. 使用 gate executor 验证零间隔轮次边界仍能暂停、恢复和停止。
7. 将现有“间隔过小”的 `9 ms` 拒绝测试改为 `-1 ms`。

在应用与 Web 集成测试中补充：

- 控制器接受 `intervalMs=0` 并在终态快照原样保留。
- 保存数据时元数据写出 `repeat_delay_ms=0`。
- WebSocket `start` 接受 `0`、拒绝 `-1`。
- `maxCycles=0` 继续表示无限轮次，与 `intervalMs=0` 相互独立。

## 2. 放宽零间隔并保持严格串行

将 BIZ、应用控制器、WebSocket 参数校验和前端校验统一为：

```text
intervalMs: 0..3600000
maxCycles:  0..1000000000
```

BIZ 循环保持以下顺序：

```text
执行完整 executeCycle
→ 处理结果/错误
→ 检查 maxCycles
→ intervalMs > 0 时可中断等待
→ intervalMs == 0 时让出一次线程调度并检查暂停/停止
→ 开始下一轮
```

零间隔分支使用 `QThread::yieldCurrentThread()` 和现有 `IRunControl::checkpoint()`：

- 不调用 `QCoreApplication::processEvents()`。
- 不创建嵌套 `QEventLoop`。
- 不使用 `QTimer::singleShot(0)` 驱动硬件调用。
- 不改变一次活动 `executeStep()` 的协作取消上界。

前端提示改为：

```text
0–3,600,000 ms；0 表示上一轮完成后立即开始下一轮
```

轮数提示继续为：

```text
0 表示持续运行
```

## 3. 增加兼容的批传协商

`hello` 追加可选 capability：

```json
{
  "v": 1,
  "type": "hello",
  "server": "hwtest_web",
  "protocolVersion": 1,
  "capabilities": {
    "telemetryBatch": {
      "version": 1,
      "maxSamples": 64,
      "maxBytes": 32768,
      "maxLatencyMs": 20,
      "snapshotIntervalMs": 100
    }
  }
}
```

增加 Web 层本地动作：

```json
{
  "v": 1,
  "type": "request",
  "id": "...",
  "action": "setTelemetryDelivery",
  "params": {"mode": "batch"}
}
```

支持 `single`、`batch` 两种模式：

- 每个新连接默认 `single`。
- 只允许在没有活动测试、没有待发样本时切换。
- 该动作不进入应用控制器，不占用全局硬件 busy 状态。
- 新前端只在 hello 明确声明 capability 时协商。
- 协商完成后再请求 `testConfigs` 和执行自动加载。
- 协商失败时记录诊断并安全回退到 `single`。

## 4. 定义并实现样本批消息

新增：

```json
{
  "v": 1,
  "type": "sampleBatch",
  "firstSeq": 101,
  "lastSeq": 120,
  "samples": [
    {
      "taskId": "...",
      "stepId": "...",
      "channelId": "...",
      "timestampUs": 1785000000123456,
      "cycleIndex": 1,
      "values": {},
      "tags": {}
    }
  ]
}
```

约束：

- `samples` 非空且最多 64 条。
- `lastSeq == firstSeq + samples.length - 1`。
- 序号必须是 JavaScript 安全整数且不得溢出。
- 每条样本在入队时分配序号，不在 flush 时重新编号。
- 批内顺序与 `sampleReceived` 顺序完全一致。
- 批次不得跨 `taskId`；任务变化前强制 flush。
- 每个样本字段与现有 `sample.sample` 完全相同。
- 不丢字段、不降采样、不合并相邻样本。

任一条件触发 flush：

- 距首条样本达到 20 ms。
- 达到 64 条。
- 紧凑 JSON 预计达到 32 KiB。
- `taskId` 变化。
- 进入暂停、停止、错误或终态。
- 执行 disconnect、quit 或连接关闭。

单条样本自身超过 32 KiB 时允许单元素批次超过软批大小，但不得截断或静默丢弃。

同时修复现有 `snapshot.seq`、`sample.seq` 未完整检查 JavaScript 安全整数的问题。

## 5. 合并运行态快照

批传模式下：

- `phase == running` 的普通 `cycleIndex/progress/result` 快照只保留最新值，最多每 100 ms 投影一次。
- 这些快照是“当前状态投影”，不是必须完整保留的事件日志。
- 快照源序号仍在每次 `snapshotChanged` 时递增；客户端看到跳号表示中间运行态快照被协商式合并。
- `single` 兼容模式保持现有逐快照行为。

以下事件不得合并或延迟：

- 初始 hello 后快照。
- 开始成功后的首个运行快照。
- pause/resume 状态变化。
- errorCode、dataSaveError 或安全状态变化。
- finished、stopped、error 等终态。
- 分析状态进入终态。
- disconnect/quit/异常掉线的安全收尾状态。

STOP 正常顺序固定为：

```text
尾部 sampleBatch
→ 最终 snapshot
→ stop/disconnect/quit reply
→ 必要时 WebSocket close
```

## 6. 增加有界 FIFO 与背压

`WebSocketServerOptions` 尾部追加可测试配置，默认：

```text
maxBatchSamples       = 64
maxBatchBytes         = 32 KiB
maxBatchLatencyMs     = 20
snapshotIntervalMs    = 100
socketHighWaterBytes  = 1 MiB
socketLowWaterBytes   = 256 KiB
maxQueuedOutputBytes  = 4 MiB
```

实现要求：

- 所有活动客户端的样本批次、关键快照和控制 reply 进入同一个 FIFO，保证调用顺序。
- 只在 WebSocket server 亲和线程操作 `QWebSocket` 和定时器。
- `bytesToWrite()` 达到高水位时暂停向 Qt socket 继续提交。
- `bytesWritten()` 降到低水位后恢复。
- 不阻塞等待网络 drain。
- 不跨线程发送。
- 不把旧连接 epoch 的待发内容交给重连客户端。
- 达到硬上限时禁止静默丢样本：记录 `telemetry_backpressure`，触发现有安全停止/清理并关闭连接。
- 不增加服务器历史缓存或重放能力。

采集保存和分析仍在 Web 投影前完成，因此 Web 批量器或浏览器故障不得改变 TXT、分析输入和测试判定。

## 7. 前端批量摄入与完整性检测

`HwtestClient` 同时解析旧 `sample` 和新 `sampleBatch`：

- 严格检查批大小、首尾序号、安全整数、每个样本字段和同一 `taskId`。
- 将旧单样本统一转换为内部 `samples[]` 摄入路径。
- 跟踪当前任务预期序号。
- 检测重复、倒序或缺口时不伪造完整状态；记录错误并把本次浏览器历史标记为不完整。

新增 `TelemetryStore`：

- 持有 `SampleBuffer`、最新样本、字段列表和诊断摘要。
- 记录 `receivedCount`、`retainedCount`、`evictedCount`、`sequenceComplete`。
- 提供 `appendMany()`，一批只调度一次 UI 提交。
- 样本诊断每批只生成一条摘要：首尾序号、数量、通道和轮次范围。
- 不把完整批次 payload 存入 500 条诊断缓存。
- 使用 `useSyncExternalStore` 隔离遥测刷新，避免 `RunControlBar`、应用外壳和性能页随每次遥测提交重渲染。
- 命令、错误和关键状态诊断仍可立即通知。
- 样本 UI 仍按 100 ms 加 `requestAnimationFrame` 提交。

界面增加只读统计：

```text
本次已接收
当前缓存
已淘汰
序号状态：连续 / 存在缺口 / 重连后不完整
```

终态时将前端接收数与 `snapshot.sampleCount` 对照；健康全程连接下不一致必须显示诊断。

## 8. 优化图表查询

`SampleBuffer` 增加批量追加与淘汰计数。

将当前“先构造完整窗口数组，再降采样”改成直接扫描环形缓存并产生有界绘图结果：

- 不为每张图先分配全部 50,000 点数组。
- 首尾点必须保留。
- 每个字段分别保留每桶极小值和极大值，最终使用各字段索引并集。
- 输出点数上界为 `2 × 字段数 × 像素宽度 + 首尾点`。
- 保持时间顺序、通道过滤和时间窗过滤。
- `TelemetryChart` 继续复用既有 uPlot 实例，只调用 `setData()`，不因数据更新重建图表。
